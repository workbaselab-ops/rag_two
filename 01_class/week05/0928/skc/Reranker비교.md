# 리랭커 비교: BGE · Cohere · Jina · FlashRank

> 작성 기준: 2026-09-22  
> 대상: RAG 검색 결과의 2단계 재정렬(reranking)

## 1. 리랭커란?

리랭커는 1차 검색기(BM25, 벡터 검색, 하이브리드 검색 등)가 뽑은 후보 문서를 **질문과의 관련도 순으로 다시 정렬**하는 모델이다.

일반적인 RAG 흐름은 다음과 같다.

```text
사용자 질문
  → 1차 검색: 전체 문서에서 후보 top_k(예: 20~100개) 추출
  → 리랭킹: 질문과 각 후보 문서를 함께 평가
  → 최종 top_n(예: 3~10개) 선택
  → LLM에 컨텍스트로 전달
```

임베딩 검색은 질문과 문서를 각각 벡터로 만들어 빠르게 비교하는 반면, 전형적인 **Cross-Encoder 리랭커**는 `[질문, 문서]`를 한 번에 읽고 관련도 점수를 계산한다. 따라서 문맥과 단어 간 상호작용을 더 정밀하게 볼 수 있지만, 후보 문서마다 추론해야 하므로 느리고 비용이 더 든다.

> 핵심: 리랭커는 전체 문서를 검색하는 도구가 아니라, **이미 검색된 소수 후보의 순위를 정교하게 다듬는 도구**다.

## 2. 비교 대상의 정확한 의미

네 이름은 같은 추상화 수준이 아니다.

| 항목 | 실제 의미 | 실행 위치 |
|---|---|---|
| `CrossEncoderReranker` + `BAAI/bge-reranker-v2-m3` | LangChain 재정렬 컴포넌트 + 오픈 웨이트 Cross-Encoder 모델 | 주로 로컬/자체 서버 |
| `CohereRerank` + `rerank-multilingual-v3.0` | LangChain 연동 컴포넌트 + Cohere 관리형 API 모델 | 외부 API |
| `JinaRerank` + `jina-reranker-v2-base-multilingual` | LangChain 연동 컴포넌트 + Jina 모델/API | API 또는 조건부 로컬 |
| `FlashrankRerank` + `ms-marco-MultiBERT-L-12` | LangChain 연동 컴포넌트 + FlashRank의 경량 ONNX 런타임/모델 | 로컬 CPU 중심 |

즉, `CrossEncoderReranker`, `CohereRerank`, `JinaRerank`, `FlashrankRerank`는 주로 **사용 인터페이스**이고, 뒤의 이름이 실제 점수를 만드는 **모델 또는 API 모델 ID**다.

> 위의 크기와 문맥 길이는 각 프로젝트가 공개한 값이다. 실제 지연 시간과 검색 품질은 하드웨어, 배치 크기, 청크 길이, 후보 수, 데이터 도메인에 크게 좌우되므로 표만으로 절대 순위를 정하면 안 된다.

## 4. 모델별 상세 비교

### 4.1 CrossEncoderReranker — `BAAI/bge-reranker-v2-m3`

#### 개념

`CrossEncoderReranker`가 질문과 각 문서의 쌍을 모델에 전달하고, `bge-reranker-v2-m3`가 관련도 점수를 출력한다. BGE 공식 모델 카드는 이 모델을 다국어·경량 리랭커로 분류하며, 약 0.6B 파라미터와 Apache-2.0 라이선스를 명시한다.

#### 사용성

- `sentence-transformers`, Hugging Face Transformers 또는 BAAI의 `FlagEmbedding`으로 로컬 실행할 수 있다.
- LangChain에서는 현재 프로젝트처럼 `CrossEncoderReranker`에 Cross-Encoder 구현체를 주입해 사용할 수 있다.
- GPU에서 FP16과 배치 추론을 사용하면 처리량을 높이기 좋다. CPU에서도 가능하지만 후보 수와 문서 길이가 늘면 지연 시간이 빠르게 커진다.
- 모델 최대 길이는 8,192 토큰이지만 제작자는 학습 길이를 고려해 `max_length=1024`를 권장한다. 긴 문서를 무조건 8,192 토큰으로 넣기보다 적절히 청크화하는 편이 안전하다.

#### 장점

- 데이터와 모델을 내부 인프라에 둘 수 있어 보안·규제 대응에 유리하다.
- 한국어를 포함한 다국어 검색에 사용할 수 있다.
- Apache-2.0이라 상업적 자체 호스팅의 라이선스 제약이 비교적 적다.
- 파인튜닝, 양자화, 배치 크기 등 운영 제어 범위가 넓다.

#### 단점

- 각 후보를 모두 평가해야 하므로 GPU 메모리와 추론 시간이 든다.
- 모델 다운로드, 서빙, 모니터링, 스케일링을 직접 담당해야 한다.
- 긴 입력의 이론상 지원 길이와 최적 품질·속도를 내는 권장 길이는 다르다.

#### 적합한 경우

- 문서를 외부 API로 보낼 수 없는 환경
- 오픈소스 라이선스로 상용 자체 호스팅이 필요한 경우
- GPU를 사용할 수 있고 한국어/다국어 품질을 우선하는 경우

### 4.2 CohereRerank — `rerank-multilingual-v3.0`

#### 개념

Cohere가 호스팅하는 리랭크 API에 질문과 문서 목록을 보내고 정렬된 인덱스와 관련도 점수를 받는다. 모델 인프라를 직접 운영하지 않아도 된다.

#### 사용성

- API 키만 있으면 빠르게 도입할 수 있고, CPU/GPU 프로비저닝이 필요 없다.
- 문자열뿐 아니라 반구조화 데이터에도 사용할 수 있다.
- v3.0의 컨텍스트 길이는 질문과 개별 문서를 합쳐 4,096 토큰이다.
- API는 한 요청에 1,000개를 넘는 문서를 보내지 않을 것을 권장한다. 실제 RAG에서는 비용과 지연을 위해 그보다 훨씬 작은 후보 집합을 쓰는 편이 일반적이다.
- **버전 주의:** 2026-09-22 기준 Cohere 문서에는 v4.0과 v3.5가 더 최신 모델로 안내된다. 기존 시스템 호환성 때문에 v3.0을 고정하는 것이 아니라면 최신 모델도 함께 벤치마크해야 한다.

#### 장점

- 구현과 운영이 가장 단순한 편이다.
- 별도 GPU 없이 트래픽 변화에 대응하기 쉽다.
- 다국어와 구조화된 문서 리랭킹을 지원한다.
- 모델 서빙, 업데이트, 장애 대응 부담이 작다.

#### 단점

- 문서가 외부 서비스로 전송되므로 개인정보·기밀정보 정책 검토가 필요하다.
- 네트워크 지연, API 장애, 호출 한도에 영향을 받는다.
- 사용량에 따라 지속적인 비용이 발생하며 공급자 종속성이 생긴다.
- 모델 내부, 가중치, 추론 최적화와 파인튜닝을 직접 제어하기 어렵다.

#### 적합한 경우

- 빠른 PoC와 짧은 개발 기간이 중요한 경우
- GPU 운영 인력이 없거나 트래픽 변동이 큰 경우
- 외부 API로 문서를 전송해도 되는 경우

### 4.3 JinaRerank — `jina-reranker-v2-base-multilingual`

#### 개념

질문과 문서를 함께 입력하는 다국어 Cross-Encoder다. Jina는 일반 텍스트 검색 외에도 코드 검색, 함수 호출 인지, Text-to-SQL 관련 벤치마크에서 경쟁력을 강조한다. Jina API로 호출하거나 공개 가중치를 로컬에서 실행할 수 있다.

#### 사용성

- API 방식은 간단하고, 로컬에서는 Transformers, Sentence Transformers, ONNX 등을 사용할 수 있다.
- 기본 컨텍스트는 1,024 토큰이며, 더 긴 텍스트는 슬라이딩 윈도로 나누어 평가한다.
- Hugging Face 예제의 로컬 로드는 `trust_remote_code=True`를 사용한다. 운영 환경에서는 원격 코드를 검토하고 모델 리비전을 고정하는 것이 좋다.
- **라이선스 주의:** 공개 모델 가중치는 CC BY-NC 4.0으로 연구·평가 목적이다. 상업 이용은 Jina API, AWS/Azure 상품 또는 별도 계약 조건을 확인해야 한다.

#### 장점

- 다국어 검색뿐 아니라 코드·구조화 작업까지 폭넓게 고려할 수 있다.
- API와 자체 실행 중 배포 방식을 선택할 수 있다.
- BGE보다 작은 약 0.3B급 모델이며 ONNX 변형도 제공된다.
- 긴 문서에 대한 슬라이딩 윈도 처리가 모델 구현에 포함되어 있다.

#### 단점

- 공개 가중치의 비상업 라이선스는 상용 자체 호스팅에 큰 제약이 될 수 있다.
- 로컬 실행 시 사용자 정의 코드 신뢰 설정과 의존성 관리가 필요하다.
- 슬라이딩 윈도는 긴 문서를 처리할 수 있게 하지만 추론 횟수와 지연 시간도 늘린다.
- API를 사용하면 Cohere와 마찬가지로 데이터 반출과 공급자 의존 문제가 있다.

#### 적합한 경우

- 연구·평가 또는 라이선스가 해결된 환경
- 다국어와 코드/SQL 관련 검색을 함께 다루는 경우
- API와 로컬 배포를 모두 검토하고 싶은 경우

### 4.4 FlashrankRerank — `ms-marco-MultiBERT-L-12`

#### 개념

FlashRank는 가벼운 로컬 리랭킹을 목표로 하는 라이브러리다. ONNX Runtime을 이용해 별도 Torch/GPU 없이도 Cross-Encoder 계열 모델을 실행하기 쉽다. `ms-marco-MultiBERT-L-12`는 약 150MB이며 100개 이상 언어를 지원하는 다국어 선택지다.

#### 사용성

- 설치와 로컬 실행이 간단하고 CPU 중심 환경, 소규모 서버, 서버리스에 적합하다.
- 모델이 작아 다운로드, 콜드 스타트, 메모리 부담이 상대적으로 낮다.
- FlashRank 프로젝트는 이 모델을 다국어용으로 안내하면서 영어 전용 검색에는 다른 모델 사용을 권고한다.
- `max_length`를 크게 잡으면 정확도에 도움이 될 수 있지만 CPU 지연과 메모리 사용량이 커지므로 짧은 청크와 작은 후보 집합부터 시작하는 것이 좋다.

#### 장점

- 네트워크 호출과 API 키 없이 로컬에서 실행할 수 있다.
- GPU가 없어도 운영하기 쉽고 비용 예측이 단순하다.
- 모델 파일이 작아 에지·서버리스·개발자 노트북에서 시작하기 좋다.
- 민감한 문서가 외부로 나가지 않는다.

#### 단점

- 경량화의 대가로 어려운 도메인이나 미묘한 관련성 판단에서 더 큰 최신 모델보다 품질이 낮을 수 있다.
- `ms-marco` 계열 학습 데이터와 실제 사내 한국어 문서의 도메인 차이가 클 수 있다.
- 프로젝트 문서상 상세 벤치마킹이 아직 충분하지 않다고 명시되어 있어 자체 평가가 특히 중요하다.
- 모델별 라이선스와 배포 산출물의 조건을 별도로 확인해야 한다.

#### 적합한 경우

- CPU-only, 온프레미스, 에지 또는 서버리스 환경
- 매우 낮은 인프라 비용과 빠른 응답이 최우선인 경우
- 검색 품질의 일부를 양보하더라도 간단한 로컬 배포가 필요한 경우

## 5. 상황별 권장안

| 상황 | 우선 검토 | 이유 |
|---|---|---|
| 빠르게 PoC를 완성해야 함 | Cohere | 인프라 없이 API로 즉시 적용 가능 |
| 민감한 사내 문서, 외부 전송 금지 | BGE 또는 FlashRank | 완전한 로컬 처리 가능 |
| 상용 자체 호스팅 + 다국어 품질 | BGE | Apache-2.0과 높은 배포 자유도 |
| GPU 없음, CPU 비용/지연 최우선 | FlashRank | 작고 ONNX 기반인 로컬 모델 |
| 코드·SQL·다국어 검색 | Jina와 BGE를 실측 비교 | Jina가 해당 작업을 강조하지만 라이선스 검토 필요 |
| 운영 인력 부족, 트래픽 변동 큼 | Cohere | 모델 서빙과 확장 운영을 서비스가 담당 |
| 긴 문서가 많음 | 먼저 청크 전략 개선 후 BGE/Jina/Cohere 비교 | 최대 토큰 수보다 정보 보존 방식과 비용이 더 중요 |
| 최고의 한국어 품질이 목표 | BGE·Cohere·Jina A/B 평가 | 공개 벤치마크보다 실제 사내 질의 분포가 중요 |

### 현실적인 기본 선택

1. **상용·보안·자체 호스팅:** `BAAI/bge-reranker-v2-m3`
2. **가장 빠른 도입과 낮은 운영 부담:** Cohere API. 단, 새 프로젝트라면 v3.0뿐 아니라 최신 v4.0 계열도 비교
3. **CPU-only 또는 작은 배포 크기:** FlashRank의 `ms-marco-MultiBERT-L-12`
4. **연구/평가 및 코드·SQL 검색:** Jina. 상용 사용 전 라이선스부터 해결

이 권장은 출발점일 뿐이다. 최종 선택은 동일한 검색 후보와 동일한 평가셋으로 측정한 결과를 따라야 한다.

## 6. 선택 기준 체크리스트

### 6.1 검색 품질

- 한국어 오탈자, 약어, 고유명사, 숫자·날짜를 잘 구분하는가?
- 질문과 정답 문서의 표현이 크게 달라도 올바르게 올리는가?
- 유사하지만 답이 없는 문서를 아래로 내리는가?
- 코드, 표, JSON, SQL, 제품명 등 실제 문서 형식을 잘 처리하는가?

### 6.2 지연 시간과 처리량

- p50뿐 아니라 p95/p99 응답 시간은 목표를 만족하는가?
- 후보 수가 20 → 50 → 100으로 늘 때 지연이 어떻게 변하는가?
- 로컬 모델은 배치 크기, CPU 스레드, GPU 메모리까지 포함해 비교했는가?
- API 모델은 네트워크 왕복과 재시도 시간을 포함했는가?

### 6.3 비용

- API 호출비와 자체 서버비를 **월간 실제 트래픽** 기준으로 비교했는가?
- GPU 유휴 시간, 운영 인건비, 모델 다운로드/콜드 스타트도 포함했는가?
- 1차 검색의 후보 수를 줄였을 때 품질 대비 비용이 어떻게 변하는가?

### 6.4 보안·규정·라이선스

- 문서나 질의를 외부 API로 전송할 수 있는가?
- 데이터 보관, 리전, 개인정보 처리 계약이 요구사항에 맞는가?
- 모델 가중치의 상업 이용과 재배포가 허용되는가?
- 원격 사용자 정의 코드를 실행할 경우 리비전 고정과 코드 검토를 했는가?

### 6.5 운영성

- 장애 시 리랭킹을 생략하고 1차 검색 결과로 폴백할 수 있는가?
- 모델/API 버전을 고정하고 변경 전 회귀 테스트를 하는가?
- 점수 절댓값을 모델 간 공통 임계값으로 오해하지 않는가?
- 질의 유형, 문서 길이, 언어별 품질과 지연을 관측할 수 있는가?

## 7. 권장 평가 방법

### 7.1 평가셋

실제 서비스 로그를 익명화해 최소 수백 개의 질의를 만들고, 각 질의에 대해 관련 문서의 등급을 표시한다. 단순한 정답/오답뿐 아니라 다음과 같이 3단계 이상이 좋다.

- `2`: 질문에 직접 답하는 문서
- `1`: 부분적으로 관련된 문서
- `0`: 관련 없는 문서

한국어, 영문 혼합, 오탈자, 짧은 키워드, 긴 자연어 질문, 표·코드가 포함된 질문을 실제 비율대로 담는다.

### 7.2 핵심 지표

| 지표 | 의미 |
|---|---|
| nDCG@k | 관련도 등급과 순서를 함께 평가; 리랭커 비교의 핵심 |
| MRR@k | 첫 정답 문서가 얼마나 위에 있는지 평가 |
| Recall@k | 정답 문서가 최종 후보 안에 남았는지 평가 |
| p95 latency | 사용자가 경험하는 느린 요청의 지연 시간 |
| 비용/1,000 질의 | API 또는 인프라 비용의 실질 비교 |

리랭커는 1차 검색에 없는 문서를 새로 찾아낼 수 없다. 따라서 `검색 Recall@candidate_k`가 먼저 충분한지 확인한 뒤 리랭커의 nDCG/MRR 개선량을 측정해야 한다.

### 7.3 동일 조건 비교 예시

```text
1차 검색 후보 수: 30
최종 문서 수: 5
문서 청크 길이/중첩: 모든 모델에 동일
평가 지표: nDCG@5, MRR@5, Recall@5, p50/p95 latency, 질의당 비용
워밍업: 로컬 모델은 별도 측정
반복: 질의당 여러 번 실행해 평균과 분산 기록
```

모델 점수의 범위와 보정 방식은 서로 다르므로 **점수 숫자 자체를 모델 사이에서 비교하지 말고**, 정렬 결과와 실제 정답 지표를 비교한다.

## 8. 운영 권장값

- 1차 검색 `top_k`: 우선 20~50에서 시작
- 리랭킹 후 `top_n`: LLM 컨텍스트와 과제에 따라 3~10
- 긴 문서: 무작정 최대 토큰까지 투입하지 말고 의미 단위 청크 사용
- 배치: 로컬 GPU는 가능한 한 배치 처리, API는 제공 한도 내 묶음 요청
- 캐시: 반복 질문이 많고 문서 인덱스가 안정적이면 결과 캐시 고려
- 폴백: 타임아웃이나 API 장애 시 원래 검색 순위를 사용
- 버전 관리: 모델 ID, 라이브러리 버전, 토크나이저, `max_length`를 함께 고정

후보 수를 크게 늘리면 품질이 항상 좋아지는 것은 아니다. 리랭킹 비용은 대체로 후보 수에 비례하므로, `candidate_k`는 Recall이 포화되는 최소 지점을 실험으로 찾는 것이 좋다.

## 9. 결론

- **BGE v2-m3:** 다국어 품질, 보안, 상용 자체 호스팅의 균형이 좋다. 대신 모델 운영과 연산 자원이 필요하다.
- **Cohere multilingual v3.0:** 가장 간단하게 운영 가능한 관리형 옵션이다. 외부 전송, 종속성, 누적 비용을 검토하고 최신 세대와도 비교해야 한다.
- **Jina v2 base multilingual:** 다국어와 코드·구조화 검색에 매력적이고 API/로컬 선택지가 있다. 공개 가중치의 비상업 라이선스가 핵심 제약이다.
- **FlashRank MultiBERT L-12:** CPU와 작은 배포 크기에 강하다. 품질 상한과 도메인 적합성은 자체 한국어 평가로 확인해야 한다.

하나를 문서만 보고 고르기보다는 **BGE를 자체 호스팅 기준선**, **Cohere를 관리형 품질 기준선**, **FlashRank를 속도·비용 기준선**으로 먼저 측정하고, 코드/SQL 요구가 크면 **Jina를 추가**하는 방식이 효율적이다.
